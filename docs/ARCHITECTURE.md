## Neon and authorization

Use versioned, portable PostgreSQL migrations and a small approved Postgres driver. Give the API a least-privileged runtime role, use parameterized queries and pooled connections for requests, and keep direct/admin credentials for migrations and recovery. Keep transactions short. Add features' tables when each phase needs them. Neon Free currently provides 100 CU-hours per project per month, 1 GB of Postgres storage per project subject to an organization cap, and 5 GB of public transfer per project per month. Measure wakeups, compute and transfer before committing to a polling cadence. [Neon pooling](https://neon.com/docs/connect/connection-pooling), [Neon plans](https://neon.com/docs/introduction/plans)

1. In Phase 2, confirm whether any Supabase project ever ran the old migration. Inventory schema, row counts, roles and dependencies with read-only access. Review schema guidance before applying a new migration. Create a Neon development branch and rehearse from empty PostgreSQL first.
2. If hosted records exist, take an authorized encrypted export and rehearse an application-table restore into staging. Map each verifiable legacy Google identity to an internal user ID using the provider subject. Quarantine unresolved identity mappings for review. Validate counts, foreign keys, permissions, vote uniqueness and sample user journeys. Keep the source intact through acceptance and retain a tested restore point. If only device data exists, keep the local reader until an opt-in import can preserve eligible data with explicit provenance.
3. Cut over only after staging parity and a documented rollback rehearsal. Keep the previous app or API available during validation. If the destination has accepted writes, freeze writes and reconcile them before reverting. Verify recovery against a branch or backup before any irreversible operation. [Neon Supabase migration guide](https://neon.com/docs/import/migrate-from-supabase)

Use one API authorization path for web and native. Check membership, participant identity, role, lifecycle and deadline on each sensitive operation. Use foreign keys and unique constraints for membership, votes and event mappings. Serialize writes with conditional updates or a row lock and monotonically increasing meetup and round versions. Redeem expiring invite digests in the same transaction as membership creation. Give Quick Catch-up guests scoped, revocable sessions. Exact origins, availability and Calendar credentials are private. Return only the travel summaries or free/busy overlap needed for the meetup. Minimize collection, define retention before each feature goes live, and exercise deletion and revocation in tests.

## Google Identity and Calendar

- Use Sign in with Google for web with Google Identity Services, Credential Manager on Android, and Google's Sign-In SDK on iOS through an Expo-compatible native integration. Choose libraries when implementing each boundary, following dependency review. The backend verifies the token signature, issuer, audience and expiry using supported library behavior and validates state, nonce and PKCE where applicable. Keep an internal UUID keyed to the verified Google subject, with a unique provider identity and transactional account creation. Require the expected app client and audience configuration for each flow. Use a secure, HttpOnly cookie and CSRF protections on the web, and revocable, securely stored app session credentials on native. Logout, expired session recovery and account deletion work through the shared API. [Web token verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token), [Android sign-in](https://developer.android.com/identity/sign-in/credential-manager-siwg-implementation), [iOS backend authentication](https://developers.google.com/identity/sign-in/ios/backend-auth), [Expo Google authentication](https://docs.expo.dev/guides/google-authentication/)
- Calendar is optional and requests separate, incremental consent. Use the backend web-server OAuth flow in the system browser, bound to the signed-in app user and verified Google identity. Start with the narrowest event scope that supports the chosen calendar. Ask separately for free/busy. Encrypt refresh tokens with backend-managed keys. In the same transaction as confirmation, rescheduling, destination change, cancellation or participant withdrawal, enqueue versioned calendar work for eligible members. Use a unique event mapping and stable client-generated Google event ID per connection and meetup, reconcile duplicate inserts, and process durable retries with a scheduled worker. Verify autonomous processing within free hosting limits and measure its effect on Neon suspension. Support reconnect and explicit manual `.ics` export. External OAuth projects in Testing generally issue seven-day refresh tokens for Calendar scopes. [Google OAuth expiry](https://developers.google.com/identity/protocols/oauth2#expiration), [web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [Calendar scopes](https://developers.google.com/workspace/calendar/api/auth), [scheduled jobs](https://developers.cloudflare.com/workers/configuration/cron-triggers/)

## Meetup lifecycle and routing

Use server-owned lifecycle transitions. The sequences describe the normal path. Organizers may provide a known schedule or explicitly select a known venue before comparison.

| Meetup | Normal path |
| --- | --- |
| Quick Catch-up | Draft → collect approximate areas or current location and preferences → discover → explicitly select one venue or lock up to three → collect any missing travel inputs → compare when needed → confirm → complete. |
| Planned Meetup | Draft → collect availability → propose and confirm schedule → discover destinations → vote → lock up to three → collect travel inputs → compare → confirm destination → finalize arrangements → confirm meetup → complete. |

Make cancellation available from relevant active stages. A reschedule returns to the affected scheduling stage, invalidates dependent decisions as needed, and keeps prior rounds in history. A known venue enters the route stage only after it is explicitly persisted as the sole authorized candidate. Use IANA timezones for recurring availability and store confirmed instants in UTC with the meeting timezone. An organizer's missed deadline uses the round's documented closing policy. Preserve action visibility and allow eligible participants to continue asynchronously.

1. Approximate areas and group preferences determine one or two targeted Places searches for roughly 10–20 candidates. Use straight-line distance and maximum distance from independently sourced inputs for preliminary convenience. Label estimates and unknowns. Discovery, candidate views, conventional or swipe voting, and minigames make **zero Routes API calls**.
2. Close the initial ballot transactionally. Apply the configured scoring and deterministic tie rule across eligible votes and valid candidates. Store up to three finalist candidate IDs at a new round version. Detailed participant origins and intended modes are collected after this lock in Planned Meetups. Quick Catch-ups may reuse explicitly authorized current locations.
3. The API alone requests routes. Check actor and meetup access, active stage, round version, persisted finalist IDs, validated origin records, mode, operation type and quota. Resolve provider IDs and routing inputs from authoritative records. Comparison batches contain only authorized finalists and compatible modes, times and routing options, within the provider's per-request element and waypoint limits. Request detailed directions only for the chosen venue and requested participant after selection. Selection itself causes zero route requests. Keep unavailable fares explicit, including incomplete Philippine transit and ride-hailing coverage. [Route Matrix limits](https://developers.google.com/maps/documentation/routes/compute_route_matrix)
4. Atomically reserve quota and claim an idempotent job keyed by round, finalist set, operation and travel-input versions before dispatch. Revalidate under the meetup's serialization rule. Close/reopen and dispatch must coordinate so reopening blocks new claims and settles any claimed call before committing the new voting stage. Discard stale results, preserve the fact that submitted calls may have been billed, and require another lock after voting reopens. Keep DB locks out of network waits. Fail closed if a claimed call has an uncertain outcome.
5. Test the boundary with a recorded or fake provider transport and zero spend. Assert zero calls during discovery, votes and games. Reject stale revisions, arbitrary coordinates, eliminated candidates, extra modes, unauthorized actors and more than three destinations. Check concurrency, duplicate requests, reopened voting, selected-only details, usage exhaustion and ambiguous failures. Use a bounded live test only after configuration and quota checks.

For asynchronous collaboration, refresh on focus and after writes. Add version-aware adaptive polling only on active planning screens where needed. Stop it in the background. Put swipe votes through the same ballot rules with accessible controls. For typing races, first validate a small WebSocket path in the chosen runtime. Send transient progress there and persist deadlines, eligibility, reconnect anchors and authoritative outcomes in Neon. Keep race privileges limited to a tie-break, nomination or display order, with a conventional voting path.

## Google Maps usage and cost

Use Maps JavaScript API on web and the Google provider via an approved Expo-compatible wrapper on Android and iOS. Evaluate `react-native-maps` against the installed SDK and both signed native builds. Use device/browser geolocation after user action. Keep one lazy map per active planning surface, preserve camera and update markers or overlays in place. Use Google Maps URLs for explicit navigation. [Expo native mapping](https://docs.expo.dev/versions/v54.0.0/sdk/map-view/), [Maps URLs](https://developers.google.com/maps/documentation/urls/get-started)

Use separate restricted keys for each app target and backend environment. Broker Places, optional Geocoding and Routes through the authenticated API. Debounce and scope autocomplete, use the documented session pairing and Places field masks, and fetch details only when needed. Store Google Place IDs where permitted and application-owned content with clear provenance. Default to ephemeral provider details, routes and overlays. Enable temporary storage only with an API- and field-specific retention rule confirmed under applicable terms, including expiry and attribution. Use SDK-managed map caching. [Places policies](https://developers.google.com/maps/documentation/places/web-service/policies), [Maps service terms](https://cloud.google.com/maps-platform/terms/maps-service-terms), [Autocomplete pricing](https://developers.google.com/maps/documentation/places/web-service/session-pricing)

- **Pilot estimate.** Model 50 meetups per month with six participants each. Two searches per meetup yield 100 searches. A six-by-three comparison yields 900 matrix elements across the pilot, or 120 per meetup and 6,000 per month if routed across 20 initial venues. One optional detailed route per participant adds up to 300 Compute Routes requests. Two web map opens per participant imply up to 600 Dynamic Maps loads if everyone uses web. Estimate autocomplete and selected details separately by user search sessions and field masks. Put each operation in its actual SKU, including higher-tier mode and field combinations.
- **Price baseline.** The current global list provides 10,000 free monthly billable events each for Dynamic Maps, Compute Route Matrix Essentials and Compute Routes Essentials, and 5,000 for Nearby Search Pro. Measure matrix billable units as origins × destinations per submission. Browser and native SDK loads must be measured at the provider as well as instrumented in the app. Confirm SKU, geographic terms, quotas, session behavior and billing-account usage before enabling requests. [Google Maps pricing](https://developers.google.com/maps/billing-and-pricing/pricing), [Routes billing](https://developers.google.com/maps/documentation/routes/usage-and-billing)
- **Enforcement.** Start with low configured limits and allocate development and production budgets against their shared billing exposure where applicable. Reserve estimated units with atomic per-user or guest, per-meetup, global daily and monthly SKU counters, and expensive-operation limits. Track outcome without coordinates, tokens or raw responses. Count ambiguous submissions conservatively and reserve for each bounded retry. Warn at 50%, 75%, 90% and stop at 100% of the chosen app budget. Reconcile against Google telemetry. Use provider quotas where supported, key restrictions and billing alerts, especially for client SDK calls that bypass backend counters. Alerts do not cap charges. [Google cost management](https://developers.google.com/maps/billing-and-pricing/manage-costs), [API security guidance](https://developers.google.com/maps/api-security-best-practices)
